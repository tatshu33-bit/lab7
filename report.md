## 4. Рівень 3
**4.1 Версіонування.** Поточний стан — у `posts` (поле `version`), попередні — у `post_versions` з унікальним індексом `(post_id, version)`. Редагування: (1) вставка знімка, (2) `updateOne` з `version` у фільтрі (оптимістичне блокування) і `$inc:{version:1}`. Конфлікт → 409. Відновлення версії створює нову версію (історія не втрачається). Транзакції не потрібні, тому працює й на одиночному `mongod`.

**4.2 Вкладені коментарі.** Плоский масив із `parent_id` і `depth` (≤ 3); у відповідь API перетворюється рекурсивною функцією `buildTree` у дерево `replies`, UI рендерить його тією ж рекурсією. Відповідь можлива лише на схвалений коментар — перевірка в самому фільтрі `updateOne` (`$elemMatch`), тож гонки неможливі.

**4.3 Сповіщення.** При схваленні коментаря автору поста (і автору коментаря, на який відповіли) створюється документ `notifications`; у UI — дзвінок із лічильником непрочитаних, список і «позначити прочитаними». Сповіщення при схваленні, а не при створенні, щоб автор не бачив спам.

**4.4 Геолокація.** `location` — GeoJSON `Point` + `2dsphere`. API `GET /api/posts?lon=&lat=&radius_km=` використовує `$geoNear` (відстань у відповіді); в `07_level3.js` також `$near`, `$geoWithin` (`$centerSphere`, `$box`). `$geoNear` і `$text` не можна поєднувати (обидва мають бути першою стадією).

**4.5 Аналітична панель** (`dashboard.html`, `charts.js`): картки-підсумки та 9 графіків (топ авторів, категорії, публікації й перегляди за місяцями, перегляди за днями з бакетів, статуси коментарів, теги, рейтинги, географія) без зовнішніх бібліотек; усі показники рахують pipeline в `app/src/analytics.js` (`$group`, `$bucket`, `$objectToArray`). ⟦Скриншот панелі.⟧

**4.6 RESTful API.** Перелік маршрутів — у `README.md`; коректні HTTP-коди (400, 403, 404, 409, 201), єдиний обробник помилок, відображення помилок MongoDB (121 → 400, 11000 → 409).

**4.7 Кешування.** Кеш у пам'яті сервера: TTL (30–60 с) + LRU (до 500 записів) + повне скидання при будь-якій успішній зміні даних. Заголовок `X-Cache: HIT|MISS|BYPASS`, статистика `GET /api/cache/stats`, показ у дашборді. Модульний тест перевіряє TTL, LRU та лічильники. Обмеження: кеш один на процес (для кількох інстансів потрібен Redis), перегляди в закешованому списку відстають до 30 с. Виграш: ⟦час першого та повторного запиту з дашборда, мс⟧.

**4.8 Порівняльний аналіз із PostgreSQL.** Схема — `relational/01_schema.sql`: 10 таблиць (`users, categories, tags, posts, post_tags, comments, reactions, post_versions, post_daily_views, notifications`) проти 8 колекцій; коментарі, теги й перегляди нормалізовано. Ті самі дані завантажено в обидві СУБД (`gen_pg.js`). Еквівалентні індекси: B-tree, GIN по `tsvector` (аналог `text`), GiST `earthdistance` (аналог `2dsphere`).

**Висновки.**
| Аспект | PostgreSQL | MongoDB |
|---|---|---|
| Читання сторінки поста | 5 з'єднань таблиць (`JOIN` + підзапити) | один документ — читається одним зверненням |
| Зміна «довідкових» даних (ім'я автора) | 1 рядок (3,5 мс) | оновлення поста автора та всіх його коментарів у всіх постах (Q10 у MongoDB — кількість змінених документів у `output/09_benchmark.txt`) |
| Цілісність | `FOREIGN KEY`, `CHECK`, `UNIQUE` | `$jsonSchema` + унікальні індекси; посилання перевіряє застосунок (`08_consistency.js` шукає розбіжності) |
| Складні агрегації за зв'язаними сутностями | оптимізатор `JOIN` | швидко, коли поля вбудовано; інакше `$lookup` |
| Схема | жорстка, міграції | гнучка, версіонування — поле `version` |
| Повнотекстовий пошук для української | `simple` + власний `search_stems` (як і в MongoDB) | те саме; Atlas Search з аналізатором `lucene.ukrainian` не перевірявся |

Загальний висновок: для блогу з читанням «пост + все пов'язане» документна модель природніша, але ціна — денормалізація (лічильники, імена) і ручна підтримка узгодженості. Реляційна модель сильніша для звітності та цілісності. Узгодженість лічильників у MongoDB перевіряє `08_consistency.js` (очікується 0 розбіжностей після всіх операцій рівнів 2–3).

## 6. Відповіді на контрольні запитання (стисло)
1. **Принципи проєктування.** Схема визначається патернами доступу, а не нормалізацією: що читається разом — зберігати разом; враховувати співвідношення (1:few, 1:many, M:N), швидкість зростання, частоту змін, ліміт документа 16 МБ.
2. **Вбудовування чи посилання.** Вбудовувати — малі, обмежені за кількістю дані, що читаються разом (коментарі поста). Посилатись — необмежений ріст, незалежне використання, часті зміни (реакції, версії, користувачі).
3. **Денормалізація.** Плюс — читання без `JOIN`; мінуси — дублювання, дорожчі оновлення (ім'я автора в постах і коментарях), ризик розсинхронізації.
4. **Пагінація.** `skip/limit` повільний на великих зсувах; краща — за курсором (`_id`/дата > останнього) на індексі; у pipeline — `$facet` зі сторінкою й `$count`, із стабільним сортуванням (`published_at`, `_id`).
5. **Bucket.** Групування подій часового ряду в один документ за період (у роботі — перегляди «пост × місяць»): менше документів та індексів, швидкі агрегації.
6. **Консистентність при денормалізації.** Оптимістичне блокування (`version`), атомарні `$inc`, оновлення пов'язаних копій (`arrayFilters`, `updateMany`), транзакції на replica set, періодичні перевірки (`08_consistency.js`), Change Streams.
7. **Індекси блогу.** Складені за ESR (категорія+статус+дата), за автором і датою, multikey по тегах, `text`, `2dsphere`, часткові (лише опубліковані), унікальні (`slug`, `email`).
8. **Масштабування.** Вертикальне — потужніший сервер (межа апаратури); горизонтальне — розподіл даних між вузлами (шардинг, репліки).
9. **Транзакції.** Багатодокументні ACID-транзакції — з MongoDB 4.0 (replica set) і 4.2 (шардинг); обмеження: накладні витрати, ліміт часу (60 с), блокування. Операції над одним документом атомарні завжди — тому в роботі вони вирішують більшість задач.
10. **Метрики.** Затримка (середня/перцентилі), пропускна здатність, `docsExamined` проти `nReturned`, розмір даних та індексів, час завантаження, вартість запису, використання пам'яті.
